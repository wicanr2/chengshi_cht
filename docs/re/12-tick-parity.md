# 12 — 整刻對拍：工具、現況與剩下的差距

**推論等級：已確認（工具）／強證據（結果）**。日期 2026-08-29。
接線：`internal/sim/tickparity_test.go`。

## 一、oracle 沒有「走一刻」的指令

`SimFrame()`（`s_sim.c:90`）每個 timer frame 只走**一個相位**，
而 Tcl 只能設速度（`sim Speed`）與 timer 延遲（`sim Delay`），
**沒有單步指令**。所以不能直接說「跑 N 刻然後比對」。

`sim Delay 400` 也沒用：實測把延遲拉到 400 ms 之後，五秒仍然跑了
**九個遊戲年（432 刻）**——延遲不是節流的地方。

## 二、改用亂數狀態當時鐘

亂數是 24 位元的 LCG（[`02-rng.md`](02-rng.md)），而且**可逆**：
`A = 1103515245` 是奇數，模 2²⁴ 有乘法反元素，所以狀態能往回推。
於是：

```
暫停 → 讀四次 sim Rand → 反推得到「開跑瞬間」的狀態 S0
倒出起始地圖
跑一段 → 暫停 → 讀四次 → 反推後倒退四步得到「結束瞬間」的狀態 S1
倒出結束地圖

Go 版從 起始地圖 ＋ S0 出發，逐相位推進，
找一個相位數 n 使得 亂數狀態 == S1 而且 12000 格全部相同
```

**兩個條件同時成立就是逐指令等價的強證據**：亂數狀態對上代表每一個消耗
亂數的分支都走得一樣；地圖對上代表每一次寫入都一樣。

起始的 `Fcycle`／`Scycle` 不可觀測（`GenerateSomeCity` 之後到暫停之間
可能跑了幾個 frame），所以在小範圍內搜尋。

工具：`tools/oracle/tcl/tick-parity.tcl`（產生實驗）、
`internal/sim/tickparity_test.go` 的 `rewindRand`／`modInverse24`（倒推）。

## 三、現況

實驗內容：產生地形（種子 12345）→ 暫停 → 種一座燃煤電廠、一段電線、
一條 31 格道路、三個空住宅區 → 跑約四秒 → 暫停。

| 指標 | 值 |
|---|---:|
| 原版改變的格數 | 108 |
| Go 版最接近時的差異 | **7** |
| 重現率 | **93.5%** |
| 亂數狀態對上 | **否** |

`TestTickParityBestEffort` 是回歸護欄：差異格數不得比 7 更差，
**也不得更好而不更新門檻**——修好一處就把門檻調緊。

剩下的 7 格全部落在住宅區的建物位置（`buildHouse` 挑格子時有平手擲骰），
是亂數錯開之後的下游現象，不是獨立的錯誤。

## 四、亂數對不上的已知原因

已經找到並修掉一個：**商業區成長判斷的短路順序**
（`TrfGood &&` 排在最前面，塞車時那一次 `Rand16Signed()` 根本不會被呼叫）。

還沒補的東西都會改變抽樣次數：

| 缺口 | 為什麼會影響抽樣 |
|---|---|
| 精靈系統（`w_sprite.c`）| `MoveObjects()` 每個 frame 都跑，精靈的移動與碰撞會抽樣 |
| 訊息系統（`s_msg.c`）| `CheckGrowth` 與劇本勝敗判定 |
| 玩家工具（`w_tool.c`）| 實驗裡沒用到，但完整對拍需要 |

## 五、量抽樣次數的微實驗

`tools/oracle/tcl/micro-*.tcl` 把地圖控制到最簡，量「一段時間內消耗幾個亂數」。
做法是讀前後兩個狀態，再用 LCG 往前推算兩者相距幾步。

實測（`sim Disasters 0`，空地，兩秒）：

| 地圖 | 消耗的亂數 | 地圖變化 |
|---|---:|---:|
| 完全空地 | 1403 | 0 格 |
| 一個空住宅區（無路無電）| 3000 | 0 格 |

**空地也消耗 1403 個**——那是 `CityEvaluation` 的投票
（`voteProblems` 最多 600 次 `Rand(300)`、`doVotes` 100 次 `Rand(1000)`）。
Go 版量到一次評分約 648 個，兩次約 1300，量級對得上。

> 這個工具是接下來除錯的主力：把地圖縮到只有一個要驗的機制，
> 抽樣次數就變成一個可以直接比對的數字。
