# 12 — 逐次元對拍：工具、現況與剩下的差距

**推論等級：已確認（工具與方法）／強證據（結果）**。日期 2026-08-29。
接線：`internal/sim/tickparity_test.go`、`internal/sim/segparity_test.go`、
`internal/sim/microzone_test.go`。

## 一、oracle 沒有「走一刻」的指令

`SimFrame()`（`s_sim.c:90`）每個 timer frame 只走**一個相位**，
而 Tcl 只能設速度（`sim Speed`）與 timer 延遲（`sim Delay`），
**沒有單步指令**。所以不能直接說「跑 N 刻然後比對」。

`sim Delay 400` 也沒用：實測把延遲拉到 400 ms 之後，五秒仍然跑了
**九個遊戲年（432 刻）**——延遲不是節流的地方。

## 二、亂數狀態就是時鐘

亂數是 24 位元的 LCG（[`02-rng.md`](02-rng.md)），而且**可逆**：
`A = 1103515245` 是奇數，模 2²⁴ 有乘法反元素，狀態能往回推。

更重要的是它的等價性：**LCG 的狀態由起點與步數唯一決定**，所以

> 「兩邊的亂數狀態相同」⟺「這一段消耗的抽樣次數一模一樣」

比對狀態就是在比對抽樣次數，而抽樣次數對得上，代表每一個「要不要抽」
的分支都走得一樣。再加上地圖零差異（每一次寫入都一樣），就是逐次元等價。

做法：

```
暫停 → 讀四次 sim Rand → 反推「開跑瞬間」的狀態 S0 → 倒出地圖
跑一段 → 暫停 → 讀四次 → 反推並倒退四步得到 S1 → 倒出地圖
Go 從 地圖 ＋ S0 出發逐 frame 推進，找 n 使得 狀態 == S1 且 12000 格全同
```

`Fcycle` 與 `CityTime % 48` 都不可觀測（原版沒有對應的讀取指令），
所以每次比對要對 16×48 個候選各試一遍。

工具：`tools/oracle/tcl/tick-parity.tcl`（單段）、
`tools/oracle/tcl/tick-parity-seg.tcl`（分段）、
`tools/oracle/tcl/micro-*.tcl`（微實驗）、
`tickparity_test.go` 的 `rewindRand`／`modInverse24`。

## 三、三層對拍，由細到粗

### 3.1 微實驗：單一機制（`microzone_test.go`）

空地 ＋ 一座沒有電、沒有路的 3×3 住宅區——最小的、能走完
`doResidential → Rand(35) → evalRes → growShrink → doResOut` 的配置。

**結果：692.5 刻、1538 次抽樣、地圖零差異，逐次元完全一致。**

微實驗的價值在於把變因減到一個。地圖縮到只剩一個機制，抽樣次數就變成
一個可以直接比對的數字。

### 3.2 分段對拍：短脈衝（`segparity_test.go`）

單段對拍用「地圖差幾格」當指標太粗——一次分歧之後的差異全部混在一起，
看不出是哪裡壞的。改成把同一次原版執行切成 23 段短脈衝，每段十幾刻，
接縫記下亂數狀態與地圖。

**結果：23 段裡 9 段逐次元完全對上**，包含好幾段含完整城市評估
（單次約 700 次抽樣）的段落。

對不上的多半是十幾刻的短段。那種長度裡，重建不出來的內部狀態
（`Scycle`、三個閥門、`TrfDensity`、`RateOGMem`、上一輪的
`ProblemTaken`）還來不及收斂——不一定是實作有錯。

### 3.3 整段對拍：粗略護欄（`tickparity_test.go`）

四秒的長段，只看地圖差幾格。**現況 108 格中差 8 格（92.6%）**，
亂數狀態沒對上。留著當回歸護欄，指標本身不精確。

## 四、靠這套方法抓到的錯

| 錯誤 | 症狀 | 修法 |
|---|---|---|
| 商業區成長判斷沒短路 | 塞車時多抽一次 `Rand16Signed()` | 照 C 的順序內聯 `TrfGood &&` |
| 撥款比例沒初始化成 1.0 | `roadValue` 恆為 0，資金只進不出（原版每年 −12，Go ＋9）；`RoadEffect` 也失真 | `NewWorld` 補上 `w_budget.c:82 InitFundingLevel` 的三個 1.0 |
| 投票迴圈跳過越界那一次的抽樣 | 每次評估少抽約 54 次 | 照抽不誤，比較對象取 0 |

第三項值得展開。`VoteProblems`（`s_eval.c`）的迴圈尾是

```c
x++;
if (x > PROBNUM) x = 0;     /* 不是 >= */
```

`PROBNUM` 是 10，而 `ProblemTable` 只有 `0..9`，所以 `x` 每 11 次就會走到
10、讀一次越界。**那一次的 `Rand(300)` 照樣被呼叫**，只是拿去和相鄰記憶體
比較（宣告順序是 `ProblemTable`、`ProblemTaken`、`ProblemVotes`，讀到的
多半是 `ProblemTaken[0]`，值域 `{0,1}`，幾乎永遠比不過）。

原本的 Go 寫成「索引超出範圍就跳過」——語意上看起來更安全，實際上**少抽了
一次**。每次評估最多 600 圈，等於少 54 次；亂數數列從此整條錯開。

> 教訓寫成規則：**照抄 UB 時，先分清「讀到什麼」和「有沒有讀」。**
> 讀到的值不可移植，但「有沒有消耗一次抽樣」是確定的，而且對狀態機
> 的影響遠大於那個值本身。跳過整個判斷式是把兩件事一起改掉。

## 五、怎麼定位下一個差異

1. **量速率**。長跑一段，算每刻抽幾次。原版 24.716（±0.11，
   來自 `sim Year` 只有 48 刻解析度）；Go 現在 24.820，落在區間內。
2. **拆相位**。Go 這邊可以逐 frame 記錄抽樣次數並按相位歸戶，
   看是哪個相位在耗。這座城市只有相位 2（`MapScan` 的第二段，
   三個分區中心都在裡面）與相位 9（`CityEvaluation`）在抽。
3. **對照原始碼盤點抽樣點**。`s_sim.c` 29 處、`s_zone.c` 21 處、
   `s_traf.c` 4 處、`s_eval.c` 2 處、`s_disast.c` 20 處、
   `w_sprite.c` 35 處；逐一確認在當前地圖下會不會觸發。
4. **縮到微實驗**。變因減到一個，抽樣次數就是可比對的數字。

> 反面教訓：一開始用四秒長段對拍，差異 7 格卡了很久，因為那個指標
> 同時混了「分歧點」和「分歧之後的所有下游效應」。換成短脈衝分段之後，
> 兩個真錯誤在同一輪就被定位出來。**指標的解析度決定除錯的效率。**

## 六、Scycle 也要搜，不能當 0

三種分區各做一個微實驗（住宅、商業、工業），前兩個一搜相位就對上，
**工業區搜了十六個相位全部對不上**。症狀看起來像實作錯誤：

- 抽樣總數對得上（960 刻只差 33 次，而且前面幾千次完全一致）
- 地圖完全一樣（那座分區沒電沒路，從頭到尾沒長過）
- 只有 `CrimeMaxX`／`CrimeMaxY`——平手擲骰的結果——偶爾不一樣

把原版切成二十幾個檢查點逐段追，發現前十七段完全對上，第十八段斷掉；
再逐次記下抽樣的呼叫點，看到斷點落在一個 `CrimeScan` 連抽四次的 frame
中間——原版的停點是 216 次，我們的 frame 邊界從 213 直接跳到 217。

原因不在工業區，在**起始狀態少設了一個變數**：

```c
case 12: if (!(Scycle % SpdPtl[x])) PTLScan();
case 13: if (!(Scycle % SpdCri[x])) CrimeScan();
case 14: if (!(Scycle % SpdPop[x])) PopDenScan();
case 15: if (!(Scycle % SpdFir[x])) FireAnalysis();
case 11: if (!(Scycle % SpdPwr[x])) DoPowerScan();
```

最快速度下這五個分別是 `Scycle % 17／18／19／20／5`。**`Scycle` 從外面
觀察不到**（Tcl 沒有對應的存取子），所以它和相位一樣是要猜的。

Scycle 錯的話會發生的事很特別：那幾個掃描落在**不同的刻**，但它們每次
抽的次數是固定的，所以**抽樣總數還是對得上**——只有它們吃到的亂數值
不一樣。於是平手擲骰的贏家換人，而其餘一切看起來都正常，直到某個檢查點
的停點剛好落在我們某個 frame 的中間。

把 Scycle 一起搜（1024 個值 × 16 個相位，Go 跑不到一秒）之後：

| 微實驗 | 相位 | Scycle | 結果 |
|---|---|---|---|
| 住宅區 | 12 | 0 | 692.5 刻逐次元一致，地圖零差異 |
| 商業區 | 0 | 0 | 564.2 刻逐次元一致，地圖零差異 |
| 工業區 | 0 | 6 | 949.2 刻逐次元一致，地圖零差異 |

> 教訓寫成規則：**對拍前先列出「原版有、但觀察不到」的狀態，逐一決定
> 是搜還是重建。** 沒列的那一個不會報錯，它會讓對拍在一個看起來完全
> 無關的地方失敗——而那個地方（這次是犯罪掃描的平手擲骰）會把你引去
> 讀完全正確的程式碼。

### 把 Scycle 套進分段對拍

分段對拍（§3.2）原本只搜相位與 `CityTime % 48`（16 × 48 = 768 個候選）。
加上 Scycle 是 768 × 1024 ≈ 79 萬個候選，所以先把搜尋本身弄快：

**收斂只做一次。** 原本每個候選都先跑 200 刻讓衍生陣列收斂，而那 3200 個
frame 與候選的相位／`CityTime` 無關——是整個搜尋六成的成本。提到迴圈外
之後，二十三段從一百多秒掉到十一秒（`cloneWorld`）。

⚠ 複製世界要另外配一份 `*Rand`。共用同一個亂數狀態的話，搜尋結果會隨
迴圈順序改變——那種錯誤不會噴任何訊息，只會讓「對上幾段」這個數字
時好時壞。

加了 Scycle 的版本是 `TestSegmentParityDeep`，預設跳過（一段約八分半）：

```sh
SIMCITY_DEEP=1 SIMCITY_SEGS=12,14 tools/go.sh test ./internal/sim/ \
    -run SegmentParityDeep -v -timeout 60m
```

### 搜到的解記下來，日常測試只驗不搜

`TestSegmentParityDeep` 很慢，而且「搜得到」是個弱判準——搜尋範圍夠大
時，它遲早會找到某個湊得出來的起點。所以把搜出來的
`(段, 相位, CityTime%48, Scycle)` 記進 `segSolutions`，讓日常的
`TestSegmentParity` 改成**驗**那些解：一段一個候選，二十三段不到一秒，
而且判準變強——解驗不過就代表規則層真的被動到了。

⚠ 段數只能靠 `SIMCITY_SEGS` 挑著搜。長段（一千次以上抽樣）的窮舉一段
就要一個多小時，短段（一百次上下）只要兩三分鐘。

## 六之二、接力：比逐段獨立搜更強的判準

逐段對拍每一段都用「200 刻收斂」重建內部狀態，**那是虛構的**。真正的
閥門、成長率記憶、交通密度是從上一段延續下來的，不是從那一段的起始
地圖重新算出來的。收斂只是讓數字落在合理範圍，不是讓它們正確。

而 `tools/oracle/tcl/tick-parity-seg.tcl` 顯示**段與段之間沒有玩家動作**
（只有 `Speed 3` → `Speed 0` → 讀狀態 → 倒地圖）。所以合法的做法是接力：
只在第一段搜起點，之後一路跑下去，中途什麼都不重設，地圖也不重設。

這證明的是「連續 N 段逐次元一致」，比「N 段各自在某個湊出來的起點下
一致」強得多。實作是 `TestSegmentParityChain`（1024 個 Scycle 全掃，
十秒）。

**現況：接力只連上 1 段。** 第 2 段斷在這裡：

```
要 1406 次抽樣、跑到 1426（多 20）
frame 1245：相位 223、Scycle 341、抽 0 次
frame 1246：相位 224、Scycle 342、抽 0 次
frame 1247：相位 225、Scycle 342、抽 32 次
             traffic.go:123 tryGo ×26、zone.go:122 growShrink ×1、
             zone.go:125 growShrink ×2、zone.go:206 doResidential ×3
```

我們的 frame 邊界是 1394 與 1426，原版停在 1406——**夾在同一個 frame
裡面**。原版的 `SimFrame` 一次只跑一個相位，停點應該落在 frame 邊界上，
所以這不是「停在半路」，是那一個 frame 我們抽了 32 次而原版只抽了 12 次。
差額整個落在 `tryGo`（交通尋路每走一步抽一次）。

把 Scycle 0–1023 全掃過，接力長度都是 1，所以這不是起始狀態沒猜對。

下一個實驗是**讓原版逐 frame 報數**：改一版 tcl，每跑一個 `SimFrame`
就 `Speed 0` 讀一次亂數，得到原版每個 frame 的抽樣次數。有了那個序列，
「哪一個 frame、哪一個相位開始分岔」就是查表，不必再猜。

（地圖那 5 格差異是**時間點對不上的結果，不是獨立證據**：差的正好是
`PWRBIT`（0x8000），落在腳本種下的那座煤電廠身上，而電力掃描每 5 個
Scycle 才跑一次——在錯誤的時間點比地圖本來就會看到這種差。）

## 七、診斷工具

`internal/sim/parityprobe_test.go` 有三層，資料由 `tools/oracle/` 產生後
放在 `workplace/`（不進版控），檔案不在時全部跳過：

| 測試 | 回答什麼 |
|---|---|
| `TestMicroIndSegments` | 逐檢查點追，第一個追不到的區間就是分歧點所在 |
| `TestMicroIndTrace` | 在那個區間裡逐次記下抽樣的**呼叫點**，並列出我們的 frame 邊界 |
| `TestMicroIndScycleSearch` | 把 Scycle 也納入搜尋 |
| `TestSegmentChainTrace` | 接力斷在哪一段、斷點那個 frame 抽了幾次、各是誰抽的、地圖差哪幾格（`SIMCITY_TRACE=1`）|

`tools/go.sh` 會把 `SIMCITY_*` 開頭的環境變數帶進容器，所以
`SIMCITY_DEEP`／`SIMCITY_SEGS`／`SIMCITY_TRACE` 直接寫在指令前面就行。

呼叫點的追蹤靠 `Rand.Watch`——`Rand16` 是唯一推進狀態的地方，掛一個
回呼就能逐次記下呼叫者。狀態只看得到結果，看不到來源；沒有這個鉤子
就只能猜。
