## 一、先讓 oracle 能單步

`SimFrame()`（`s_sim.c:90`）每個 timer frame 只走**一個相位**，
而原版的 Tcl 介面只能設速度（`sim Speed`）與 timer 延遲（`sim Delay`），
**沒有單步指令**。`sim Delay 400` 也沒用：把延遲拉到 400 ms 之後，
五秒仍然跑了**九個遊戲年（432 刻）**——延遲不是節流的地方。

所以早期的做法是「`Speed 3` 然後馬上 `Speed 0`」，跑幾個 frame 由事件
迴圈決定，實測一段落在 85 到 2039 次抽樣之間。段界不可控，起始的
`Fcycle`／`Scycle` 又觀察不到，只能用搜的——而搜得到是個**弱判準**，
搜尋範圍夠大時它遲早會找到某個湊得出來的起點。

正確的做法是**加觀測手段**。`tools/oracle/patches/apply.py` 給 oracle 的
原始碼加四個指令（冪等，只加觀測、不動規則）：

| 指令 | 回答什麼 |
|---|---|
| `sim Frame N` | 跑 N 個 frame（`SimFrame` ＋ `MoveObjects`），不經過事件迴圈 |
| `sim Scycle` | 五個週期性掃描的相位計數器 |
| `sim Fcycle` | 十六相位主迴圈的計數器 |
| `sim Valves` | 三個需求閥門 |
| `sim Mem <陣列> <x> <y>` | 十一張衍生陣列的某一格（地價、汙染、犯罪、人口密度、交通密度、成長率記憶、商業距離、警消覆蓋…）|
| `sim RandState` | 亂數產生器的內部狀態（低 24 位元）|
| `sim Problems` | 城市評估的分數、贊成／反對票、問題表、票數、已選旗標 |
| `sim VoteStats` | 投票兩個迴圈各抽了幾次、跑了幾圈（診斷用的計數器）|

建置改在**副本**上進行（`workplace/oracle-build/`），封存的原始碼保持
乾淨——它是規則層的一手依據，不該混進我們為了觀測加的東西。

加完之後：段界精確、起點是 0／0 不必猜、分岔點是**查表**而不是搜尋，
而且分岔的原因（閥門、衍生陣列）可以直接對照。

## 二、亂數狀態就是時鐘

亂數是 24 位元的 LCG（[`02-rng.md`](02-rng.md)），而且**可逆**：
`A = 1103515245` 是奇數，模 2²⁴ 有乘法反元素，狀態能往回推。

更重要的是它的等價性：**LCG 的狀態由起點與步數唯一決定**，所以

> 「兩邊的亂數狀態相同」⟺「這一段消耗的抽樣次數一模一樣」

比對狀態就是在比對抽樣次數，而抽樣次數對得上，代表每一個「要不要抽」
的分支都走得一樣。再加上地圖零差異（每一次寫入都一樣），就是逐次元等價。

做法：

```
暫停 → 讀四次 sim Rand → 反推「開跑瞬間」的狀態 S0 → 倒出地圖
跑一段 → 暫停 → 讀四次 → 反推並倒退四步得到 S1 → 倒出地圖
Go 從 地圖 ＋ S0 出發逐 frame 推進，找 n 使得 狀態 == S1 且 12000 格全同
```

工具：`tools/oracle/tcl/frame-parity.tcl`（逐 frame）、
`tools/oracle/tcl/micro-*.tcl`（微實驗）、
`tickparity_test.go` 的 `rewindRand`／`modInverse24`。

## 三、三層對拍，由細到粗

### 3.1 微實驗：單一機制（`microzone_test.go`）

空地 ＋ 一座沒有電、沒有路的 3×3 住宅區——最小的、能走完
`doResidential → Rand(35) → evalRes → growShrink → doResOut` 的配置。

**結果：692.5 刻、1538 次抽樣、地圖零差異，逐次元完全一致。**

微實驗的價值在於把變因減到一個。地圖縮到只剩一個機制，抽樣次數就變成
一個可以直接比對的數字。

### 3.2 逐 frame 對拍：主判準（`frameparity_test.go`、`framescen_test.go`）

單步的 oracle 讓每一個 frame 都成為一個檢查點。資料是
`tools/oracle/tcl/frame-parity.tcl` 跑 8000 個 frame，每一步記下
`Fcycle`、`Scycle`、三個閥門與四個亂數讀數；
`tools/oracle/extract_frames.py` 把四個讀數換算成**抽樣次數**
（等價，但只要幾個位元組），存成 `testdata/frame/frames.csv`。

**結果：8000/8000 個 frame 完全一致，共 13 954 次抽樣**，
終點地圖 12 000 格零差異、資金相同。

劇本版（`framescen_test.go`）載入 Dullsville 再跑同樣的 8000 個 frame：
**122 314 次抽樣，一樣 8000/8000**。那座城市有人口、交通、稅收與
週期性的城市評估，掃到的規則多得多。

⚠ **前兩份都沒有觸發精靈**（Dullsville 實測整段 0 個——沒有機場、港口與
足夠的鐵路）。第三份改用 **Tokyo**：它的劇本災難就是怪獸，所以精靈第一次
真的動起來了。東京也大得多——8000 個 frame 共 **955 206 次抽樣**，
地圖改變 2592 格，場上同時有火車、船、飛機、直昇機、怪獸與爆炸。

`sim FrameStats` 把一個 frame 的抽樣拆成「SimFrame（規則）」與
「MoveObjects（精靈）」兩段，所以「差在哪一側」是量出來的，不是猜的——
東京的分岔一路都在精靈那一側，規則層從第一個 frame 起就沒錯過。
東京現在也是 **8000/8000**，判準包含逐 frame 的精靈全欄位與地圖雜湊。

### 短版：逐 frame 比對每一隻精靈的十八個欄位

長版只知道「這個 frame 精靈那一側多抽了幾次」。短版
（`tools/oracle/tcl/frame-parity-tokyo-short.tcl` ＋ `spriteparity_test.go`）
只跑 400 個 frame，但**每個 frame 都倒出所有精靈的完整狀態**
（`sim Sprites`，十八個欄位），所以分岔時知道的是「第 N 個 frame、第幾隻、
哪個欄位」。

短版還用 `sim RandState` 直接讀亂數狀態，不像長版抽四次來反推：指令數少
四倍，而且**完全不擾動數列**，所以沒有「差 4」那個簿記。整份跑完 2.5 秒。

`sim SpriteDraws` 再把精靈那一側拆到**逐型別**（索引就是精靈型別編號），
所以連「是哪一型多抽的」都是查表。

**現況 400/400。** 長版後來也補上同樣的逐欄位判準（`S` 那一行改成每個
frame 都倒），所以兩份現在的判準一樣，短版的價值只剩「跑得快、看得細」。

⚠ **精靈的十八個欄位不含幾何**（寬高、繪圖偏移、熱點）。它們只跟型別有關，
測試載入時要用 `applyGeom` 補回去——少了熱點，`spriteNotInBounds` 會把
x = −47 的船（熱點 48，其實還在圖上）算成出界，船在第 0 個 frame 就沒了。

地圖雜湊的工具已經做好了（`sim MapHash`，在 C 裡算 FNV-1a，避開「在 Tcl 裡
逐格倒」那條死路），但把它加進逐 frame 的輸出之後，這台機器忙的時候整份
就跑不完（沒加 2.6 秒，加了跑不出來）。原因還沒查清楚——4.8M 次原生迴圈
不該這麼貴，比較可能是輸出量與 pty 的交互作用。機器閒的時候把
`[sim MapHash]` 加回 FS 那一行就能開起來。

⚠ **這些「對上幾個 frame」的數字不跨資料集比較。** 原版每次啟動會先產生
一座隨機城市，載入劇本時 `InitWillStuff` 又 `RandomlySeedRand()` 重設種子，
所以重跑一次 oracle 就是一條不同的軌跡。門檻只在資料集固定時當回歸護欄。

⚠ 劇本版的起始狀態要**從 oracle 倒**，不能只靠我們自己重建：原版那個
行程開機時已經跑過一座隨機城市，載入劇本的瞬間有一堆殘留狀態
（交通密度、成長率記憶、警消覆蓋表、`NewPower` 早就是 1…）。
`sim RandState` 讓我們從「載入之前」的亂數狀態出發，`sim Mem` 把十一張
衍生陣列倒出來，剩下的地圖差異（十來格，全是道路的車流顯示）直接用
原版的起始地圖覆蓋——這個測試要問的是**八千個 frame 的動態**，
不是載入程序（那由 `cityfile_test.go` 與 `power_test.go` 顧）。

這個判準比分段對拍強得多：分段對拍每一段都要用「200 刻收斂」重建
內部狀態，而那是虛構的——真正的閥門、成長率記憶、交通密度是從上一段
延續下來的。逐 frame 對拍從第一個 frame 一路跑到最後，中途什麼都不重設。

> 分段對拍（`segparity_test.go`、`testdata/seg/`、`tick-parity-seg.tcl`）
> 已經移除。它的起點要用搜的、段界不可控，而且判準弱——被這一節取代。

### 3.3 整段對拍：粗略護欄（`tickparity_test.go`）

四秒的長段，只看地圖差幾格。**原版改變的 108 格一格不差全部重現。**
留著當便宜的回歸護欄；嚴格的判定由 §3.2 負責。

## 四、靠這套方法抓到的錯

| 錯誤 | 症狀 | 修法 |
|---|---|---|
| 商業區成長判斷沒短路 | 塞車時多抽一次 `Rand16Signed()` | 照 C 的順序內聯 `TrfGood &&` |
| 撥款比例沒初始化成 1.0 | `roadValue` 恆為 0，資金只進不出（原版每年 −12，Go ＋9）；`RoadEffect` 也失真 | `NewWorld` 補上 `w_budget.c:82 InitFundingLevel` 的三個 1.0 |
| 投票迴圈跳過越界那一次的抽樣 | 每次評估少抽約 54 次 | 照抽不誤，比較對象取 0 |

第三項值得展開。`VoteProblems`（`s_eval.c`）的迴圈尾是

```c
x++;
if (x > PROBNUM) x = 0;     /* 不是 >= */
```

`PROBNUM` 是 10，而 `ProblemTable` 只有 `0..9`，所以 `x` 每 11 次就會走到
10、讀一次越界。**那一次的 `Rand(300)` 照樣被呼叫**，只是拿去和相鄰記憶體
比較（宣告順序是 `ProblemTable`、`ProblemTaken`、`ProblemVotes`，讀到的
多半是 `ProblemTaken[0]`，值域 `{0,1}`，幾乎永遠比不過）。

原本的 Go 寫成「索引超出範圍就跳過」——語意上看起來更安全，實際上**少抽了
一次**。每次評估最多 600 圈，等於少 54 次；亂數數列從此整條錯開。

> 教訓寫成規則：**照抄 UB 時，先分清「讀到什麼」和「有沒有讀」。**
> 讀到的值不可移植，但「有沒有消耗一次抽樣」是確定的，而且對狀態機
> 的影響遠大於那個值本身。跳過整個判斷式是把兩件事一起改掉。

## 五、怎麼定位下一個差異

1. **量速率**。長跑一段，算每刻抽幾次。原版 24.716（±0.11，
   來自 `sim Year` 只有 48 刻解析度）；Go 現在 24.820，落在區間內。
2. **拆相位**。Go 這邊可以逐 frame 記錄抽樣次數並按相位歸戶，
   看是哪個相位在耗。這座城市只有相位 2（`MapScan` 的第二段，
   三個分區中心都在裡面）與相位 9（`CityEvaluation`）在抽。
3. **對照原始碼盤點抽樣點**。`s_sim.c` 29 處、`s_zone.c` 21 處、
   `s_traf.c` 4 處、`s_eval.c` 2 處、`s_disast.c` 20 處、
   `w_sprite.c` 35 處；逐一確認在當前地圖下會不會觸發。
4. **縮到微實驗**。變因減到一個，抽樣次數就是可比對的數字。

> 反面教訓：一開始用四秒長段對拍，差異 7 格卡了很久，因為那個指標
> 同時混了「分歧點」和「分歧之後的所有下游效應」。換成短脈衝分段之後，
> 兩個真錯誤在同一輪就被定位出來。**指標的解析度決定除錯的效率。**
>
> 這條路走到底就是逐 frame：解析度到了一個 frame，「下一個差異在哪」
> 不再需要定位——它就寫在測試的輸出裡。所以上面這四個步驟現在只在
> **還沒有單步 oracle 的新題目**上才用得到；有 oracle 的話，先花半小時
> 加單步指令，比花一天用這四步定位划算。

## 六、Scycle 也要搜，不能當 0

三種分區各做一個微實驗（住宅、商業、工業），前兩個一搜相位就對上，
**工業區搜了十六個相位全部對不上**。症狀看起來像實作錯誤：

- 抽樣總數對得上（960 刻只差 33 次，而且前面幾千次完全一致）
- 地圖完全一樣（那座分區沒電沒路，從頭到尾沒長過）
- 只有 `CrimeMaxX`／`CrimeMaxY`——平手擲骰的結果——偶爾不一樣

把原版切成二十幾個檢查點逐段追，發現前十七段完全對上，第十八段斷掉；
再逐次記下抽樣的呼叫點，看到斷點落在一個 `CrimeScan` 連抽四次的 frame
中間——原版的停點是 216 次，我們的 frame 邊界從 213 直接跳到 217。

原因不在工業區，在**起始狀態少設了一個變數**：

```c
case 12: if (!(Scycle % SpdPtl[x])) PTLScan();
case 13: if (!(Scycle % SpdCri[x])) CrimeScan();
case 14: if (!(Scycle % SpdPop[x])) PopDenScan();
case 15: if (!(Scycle % SpdFir[x])) FireAnalysis();
case 11: if (!(Scycle % SpdPwr[x])) DoPowerScan();
```

最快速度下這五個分別是 `Scycle % 17／18／19／20／5`。**`Scycle` 從外面
觀察不到**（Tcl 沒有對應的存取子），所以它和相位一樣是要猜的。

Scycle 錯的話會發生的事很特別：那幾個掃描落在**不同的刻**，但它們每次
抽的次數是固定的，所以**抽樣總數還是對得上**——只有它們吃到的亂數值
不一樣。於是平手擲骰的贏家換人，而其餘一切看起來都正常，直到某個檢查點
的停點剛好落在我們某個 frame 的中間。

把 Scycle 一起搜（1024 個值 × 16 個相位，Go 跑不到一秒）之後：

| 微實驗 | 相位 | Scycle | 結果 |
|---|---|---|---|
| 住宅區 | 12 | 0 | 692.5 刻逐次元一致，地圖零差異 |
| 商業區 | 0 | 0 | 564.2 刻逐次元一致，地圖零差異 |
| 工業區 | 0 | 6 | 949.2 刻逐次元一致，地圖零差異 |

> 教訓寫成規則：**對拍前先列出「原版有、但觀察不到」的狀態，逐一決定
> 是搜還是重建。** 沒列的那一個不會報錯，它會讓對拍在一個看起來完全
> 無關的地方失敗——而那個地方（這次是犯罪掃描的平手擲骰）會把你引去
> 讀完全正確的程式碼。

### 後來 Scycle 不必再搜了

給 oracle 加上 `sim Scycle` 之後（§一），這一節的搜尋就退場了。
但**教訓不退場**：對拍前先列出「原版有、但觀察不到」的狀態，然後
**優先想辦法把它變成看得到的**——加一個唯讀存取子的成本，遠低於用
1024 個候選去搜它，也遠低於被它引去讀完全正確的程式碼。

## 六之三、需求閥門的單精度與整數除法

逐 frame 對拍上線之後，第一個分岔在**第 0 個 frame**：
`RValve` 我們算出 180，原版是 179。差 1。

而這個差 1 要跑到**第 114 個 frame** 才會變成抽樣次數的差異——那時候
某座空住宅區的 `zscore` 剛好落在成長門檻的兩側，我們多蓋了一棟房子。
在那之前，一百多個 frame 的抽樣次數完全一致。

原因在 `SetValves`（`s_sim.c:280`）兩處：

```c
float NormResPop, PjResPop, ...;
NormResPop = ResPop / 8;        /* ResPop 是 short → 整數除法！ */
```

- **`ResPop / 8` 是整數除法**，先截斷再存進 float。我們寫成
  `float64(ResPop) / 8`，多帶了小數。
- 整段是 C 的 `float`（**32 位元**），我們用 float64。幾個 double
  字面值（`.02`、`3.7`、`1.3`）還會把該次運算提升到雙精度再存回 float，
  順序也要照抄。

改成單精度 ＋ 整數除法之後，整城的粗略對拍（§3.3）直接從差 8 格
變成**差 0 格**。之前怎麼調分區規則都收不掉，因為根本不是分區的問題。

> 教訓寫成規則：**移植 C 的浮點運算時，型別就是規格。** `float` 不是
> 「浮點數」的意思，是 32 位元；`int / int` 不是除法，是截斷。
> 這兩件事都不會讓程式看起來有錯，只會讓數字差一點點——然後那一點點
> 在一百個 frame 之後變成一棟不該存在的房子。

## 六之四、對拍腳手架自己的差 4

修好閥門之後還是在第 33 個 frame 分岔，而且**閥門、地價、汙染、犯罪、
人口密度、`zscore` 全部一模一樣**（用 `sim Mem` 逐項對過）。相同的狀態
＋ 相同的亂數 = 應該有相同的結果，但沒有。

錯的是**測試的腳手架**，不是規則層：

`RecoverState` 回傳的是「**讀完那四個輸出之後**」的狀態，而原版讀完
四次 `sim Rand` 就直接跑下一個 frame——所以進入下一個 frame 的狀態
就是它。測試卻又 `advanceRand(…, 4)` 推了四步。

症狀非常隱蔽：**抽樣次數還是對得上**（偏移是常數 4，前後相減就消掉了），
只有每個 frame 實際吃到的亂數**值**整整晚四個。所以絕大多數 frame
照樣一致，直到某個分支剛好落在門檻兩側。

拿掉那四步之後：8000/8000。

> 教訓寫成規則：**對拍失敗時，先確認腳手架本身沒有引入偏移。**
> 「狀態相同、亂數相同，結果卻不同」在邏輯上不可能——出現這句話的時候，
> 「相同」的兩邊一定有一邊是自己算錯的。

## 六之五、呈現層不該和模擬共用亂數

劇本版一開始只對到第 1512 個 frame——那是第二次收稅與城市評估。症狀
非常乾淨，也非常矛盾：

- 亂數狀態一路相同（每個 frame 都比對狀態，不只比次數）
- 問題表 `ProblemTable[0..6]` 完全相同
- 投票迴圈自己的抽樣次數也相同（給 oracle 裝了計數器：603 對 603）
- 市民投票的抽樣次數也相同（100 對 100）
- **但整個 frame 原版就是多抽了一次**，而且贊成票差一票

「狀態相同、輸入相同、兩個迴圈的抽樣都相同，總數卻不同」在邏輯上不可能
——所以多出來的那一次一定在**別的地方**。搜遍原始碼的 `Rand` 呼叫點，
找到 `s_msg.c` 的 `DoMessage()`：

```c
    case  12:                       /* 交通壅塞的訊息 */
      if (Rand(5) == 1) MakeSound("city", "HonkHonk-Med");
      else if (Rand(5) == 1) MakeSound("city", "HonkHonk-Low");
      else if (Rand(5) == 1) MakeSound("city", "HonkHonk-High");
```

**挑哪一種喇叭聲，用的是模擬那顆亂數產生器。** 同樣的還有
`w_map.c`／`w_editor.c` 的地震震動位移。這些都是 X11 移植版的呈現層決定，
卻和規則層共用同一條數列。

處理方式是把它們從 oracle 拿掉（`tools/oracle/patches/apply.py` 的
`patch_ui`）：我們要的是「規則層算得對不對」，而我們自己的呈現層本來就
不共用亂數。拿掉之後，劇本版直接從 1512 跳到 **8000/8000**。

> 教訓寫成規則：**對拍對不上時，先確認你比的是同一層。** 移植版的
> UI 可能會偷用模擬的資源（亂數、計時器、全域變數）；那不是規則，
> 但它會出現在你的量測裡。原始碼裡搜一次「誰在用這個資源」比猜快得多。

## 六之六、順手抓到的兩個規則層差異

逐 frame 對拍逼出來的，不是靠讀程式碼看出來的：

- **`DoPowerScan` 不該直接寫 `PWRBIT`。** 原版（`s_power.c`）只填
  `PowerMap`；每一格的 `PWRBIT` 是下一輪 `MapScan` 在 `NewPower` 打開時
  逐格呼叫 `SetZPower` 寫的。差別只在「掃描完成」到「下一輪 MapScan」
  那幾個相位看得見——而載入城市之後正好停在那裡。
  拆成 `DoPowerScan` ＋ `ApplyPowerBits` 兩支。
- **`ProblemTaken` 要跨評估保留。** 原版是在 `VoteProblems()` **之後**
  才清零的，而投票迴圈的越界讀取 `ProblemTable[10]` 讀到的正是
  `ProblemTaken[0]`——也就是上一輪的值。（`ProblemVotes[10]` 同理會寫到
  `ProblemOrder[0]`；那一項依宣告順序推斷，推論等級**強證據**。）

## 六之七、精靈那一側的四個錯

東京這份實驗是第一個會動到精靈的對拍，一上線就從第 0 個 frame 開始對不上。
四個原因都在「載入之後的狀態」與「串列語意」，不在移動邏輯本身：

- **`InitWillStuff` 整個沒做。** 原版的 `LoadScenario`／`loadFile` 在載入
  之後會呼叫它（`s_init.c`），而它把**所有衍生陣列歸零並清掉所有精靈**
  （地價、汙染、犯罪、人口密度、交通密度、警消覆蓋、成長率記憶、商業距離）。
  少了這一步，**遊戲裡讀第二座城市會留著前一座的數字與精靈**——畫面看起來
  正常，數字全錯。這是逐 frame 對拍抓到的**真的遊戲 bug**，不只是對拍問題。
- **精靈串列的順序是反的。** 原版 `NewSprite` 是**前插**
  （`sprite->next = sim->sprite; sim->sprite = sprite`），所以 `MoveObjects`
  從最新的精靈開始跑。順序看得出來，因為 `absDist` 是所有精靈共用的一個
  全域——飛機拿「上一次算出來的距離」判斷到了沒，而那一次可能是別隻算的。
- **重用條件寫寬了。** `MakeSprite` 只有在同型別**還活著**時才原地重新
  初始化；死掉的話會生一個新節點，而 `GlobalSprites` 還指著那隻死的。
- **回收時忘了清全域。** `DestroySprite` 會把 `GlobalSprites[type]` 清成
  NULL（`w_sprite.c:403`）。

另外 `w_sprite.c` 有四個**載入時不重設**的檔案層級全域（`Cycle`、`absDist`、
`CrashX`、`CrashY`）。它們和 `Fcycle`／`Scycle` 同一類：不重設、看不到、
會影響抽樣。`sim SpriteCycle` 把它們開出來了。

> 教訓寫成規則：**「載入」是一個完整的儀式，不是把檔案的欄位填進去。**
> 原版的載入路徑上有一支專門負責清場的函式；漏掉它不會編不過、不會噴錯，
> 只會讓第二次載入之後的一切慢慢偏掉。移植時要把載入路徑**整條**讀完，
> 而不是只讀「讀檔」那一段。

## 六之八、插入順序：原始碼說前插，量出來是尾端

`w_sprite.c` 的 `NewSprite` 寫得很清楚是**前插**：

```c
sim->sprites++; sprite->next = sim->sprite; sim->sprite = sprite;
```

而 `MoveObjects` 與 `sim Sprites` 都從 `sim->sprite` 走起，所以「最新的精靈
排最前面」應該是照著讀就對的事。

**但逐 frame 逐欄位的對拍說不是。** 短版第 2 個 frame，原版的順序是
「火車、船」——船是那個 frame 才生出來的，前插的話它該排在火車前面。
把 Go 版改成前插：對到 2/400；改回尾端：54/400。

所以實作照**量出來的**走（尾端），並且在 `makeSprite` 的註解與
`CONTEXT.md` 的未解表裡記著這個衝突。**推論等級：強證據（實測），
與原始碼的字面讀法衝突，原因未解。**

換了一份資料集之後又看到第三種形狀：怪獸生出來的那個 frame，原版的第三隻
是怪獸、我們的是飛機——既不是最前面也不是最後面。

**在 oracle 裡把串列的實體順序（含死掉的節點）與 `GlobalSprites` 一起倒出來
（`sim SpritesAll` ＋ `sim SpriteGlobals`），答案就出來了**：

```
SPR 0 0 0 0 ; 1 1 -39 262 … 1 ; 8 0 0 0 … 1 ; 4 0 0 0 … 1 ; 5 0 0 0 … 1 ; 2 …
SPG -1 0 4 5 2 3 6 7 1
```

原版**開機時就把九型精靈的節點全部建好，而且都是具名的**（最後那個 1）。
具名的節點永遠不會被回收，所以：

- `MakeSprite` 從頭到尾都是**原地重用**，串列順序在載入之前就固定了；
- 「前插還是後插」根本不是主要因素——順序是開機時決定的；
- 唯一會真的插進來的是**爆炸**：它走 `MakeNewSprite`（w_sprite.c:1639），
  一定生新節點而且加在最前面。

所以對拍要把**整串（含死掉的節點）與全域指標一起倒過來**，我們的
`makeSprite` 才會在同樣的位置重用。做完之後從 46 跳到 102。

> 教訓寫成規則：**照著讀出來的結論，也要有辦法被實驗推翻。** 這一條先前
> 是「照原始碼改的」，改完長版的數字還變好了（46 → 55），看起來像佐證；
> 是後來換上更嚴的判準（逐欄位而不只是抽樣次數）才發現方向反了。
> 長版那個「變好」是同一批修改裡的其他三項帶來的。

## 六之九、oracle 的輸出走 pty 會卡，走檔案就不會

短版東京的迴圈裡加上 `[sim MapHash]` 之後，整份跑不完——**一行都不吐**，
拿掉又是 2.6 秒跑完。第一版結論寫成「MapHash 讓 oracle 跑不完，原因未解」。

**那個結論是錯的。** 做了三組對照才看清楚：

| 實驗 | 結果 |
|---|---|
| 400 次 `sim MapHash`（不 `puts`，純呼叫）| 連同 100 個 frame 一起 1.9 秒跑完 |
| 20 個 frame，一行 `puts` 帶 MapHash | 20 行，秒回 |
| 20 個 frame，**兩行** `puts` 帶 MapHash | 0 行，等滿 90 秒逾時；下一條指令一送出，40 行立刻全到 |
| 400 個 frame、兩行 `puts` 帶 MapHash，**改寫檔案** | **2.97 秒，800 行齊全** |

所以 MapHash 本身很快，慢的是 **pty 那條路**：資料明明已經產生了，卻要等
下一次寫入才被讀到。確切機制沒查出來（tty 行規則的緩衝、Tcl 的 channel、
或驅動器的提示字元切分都還有嫌疑），但**修法不必等到查清楚**：

```tcl
set fh [open /out/lines.txt w]
for {set i 0} {$i < 400} {incr i} { sim Frame 1 ; puts $fh "FS $i …" }
close $fh
```

`drive.py` 收尾時把 `/out/lines.txt` 併回結果，所以 `extract_frames.py`
那一側完全不必改。四份對拍腳本現在都走這條，長版八千個 frame 也一樣。

> 教訓寫成規則：**「加上 X 就變慢」在下結論之前，要有一組「不加 X 但條件
> 相同」的對照。** 這裡少的是「同樣的迴圈、同樣的輸出量、只是不算雜湊」，
> 補上之後才發現變因根本不是 MapHash。

## 六之十、精靈串列被重建，爆炸生出來就消失

短版東京卡在第 76／90 個 frame，症狀是**原版多一隻爆炸，我們沒有**：
怪獸走到 (66,55)，那格是 `ZONEBIT` 的商業區、`t > RZB`，
`Destroy()` 應該叫 `MakeExplosionAt()`。

但**地圖雜湊在那個 frame 是對的**——這句話把範圍縮得很小：地圖一樣，
表示 `Destroy` 的兩條寫入路徑都走了（`OFireZone` 清掉整個分區、
那一格寫成 `TINYEXP`），差的只有那隻爆炸精靈。

原因在 `MoveObjects` 的寫法：

```go
kept := s.list[:0]
for _, sp := range s.list { … kept = append(kept, sp) … }
s.list = kept          // ← 迴圈中途前插的爆炸在這裡被蓋掉
```

原版走的是鏈結串列，`MakeNewSprite` 前插的節點落在游標**後面**，
這一輪不會被走到，但**留在串列裡**。Go 版用 `s.list[:0]` 重建，
等於把迴圈期間插進來的東西整個丟掉——爆炸生出來，同一個 frame 就消失。

改成「走這一輪開始時的快照，回收時才從 `s.list` 就地摘掉」之後，
短版東京從 90/400 變成 **400/400**（含地圖雜湊）。

> 教訓寫成規則：**Go 的切片不是鏈結串列。** 照抄「走串列、順手重建」
> 這個習慣寫法，會悄悄改掉「迭代期間插入」的語意——而那正是原版
> 唯一會真的插入新節點的地方（爆炸）。

## 七、診斷工具

`internal/sim/parityprobe_test.go` 有三層，資料由 `tools/oracle/` 產生後
放在 `workplace/`（不進版控），檔案不在時全部跳過：

| 測試 | 回答什麼 |
|---|---|
| `TestMicroIndSegments` | 逐檢查點追，第一個追不到的區間就是分歧點所在 |
| `TestMicroIndTrace` | 在那個區間裡逐次記下抽樣的**呼叫點**，並列出我們的 frame 邊界 |
| `TestMicroIndScycleSearch` | 把 Scycle 也納入搜尋（有 `sim Scycle` 之後只剩歷史價值）|
| `TestFrameParityTrace` | 逐 frame 對拍分岔在哪一個 frame、那個 frame 各是誰在抽樣（`SIMCITY_TRACE=1`）|
| `TestFrameParityScenario` | 同上，但用 Dullsville 劇本；`SIMCITY_TRACE=1` 時會把我們的抽樣點與原版的投票計數並排印出來 |

`tools/go.sh` 會把 `SIMCITY_*` 開頭的環境變數帶進容器，所以
`SIMCITY_TRACE=1` 直接寫在指令前面就行。

分岔的**原因**則靠 oracle 那邊的存取子：`sim Valves` 比閥門，
`sim Mem LandValueMem x y` 之類比衍生陣列。實際用起來是「Go 印一份、
Tcl 印一份、逐項對」——第 33 個 frame 那次就是這樣確認「兩邊完全相同」，
從而把嫌疑指回測試腳手架（§6之四）。

呼叫點的追蹤靠 `Rand.Watch`——`Rand16` 是唯一推進狀態的地方，掛一個
回呼就能逐次記下呼叫者。狀態只看得到結果，看不到來源；沒有這個鉤子
就只能猜。
