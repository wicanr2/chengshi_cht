**推論等級：已確認**。日期 2026-08-29。
接線：`internal/sim/frameparity_test.go`、`internal/sim/tickparity_test.go`、
`internal/sim/microzone_test.go`。

> **結論先講：8000 個 frame（500 刻、13 582 次抽樣）逐 frame 完全一致**
> ——每個 frame 的抽樣次數、`Scycle`、三個需求閥門都相同，終點的
> 12 000 格地圖與資金也相同。整城的粗略對拍（§3.3）從差 8 格變成差 0 格。
>
> 走到這一步的關鍵是**給 oracle 加單步指令**（§一）。在那之前所有的

## 一、先讓 oracle 能單步

`SimFrame()`（`s_sim.c:90`）每個 timer frame 只走**一個相位**，
而原版的 Tcl 介面只能設速度（`sim Speed`）與 timer 延遲（`sim Delay`），
**沒有單步指令**。`sim Delay 400` 也沒用：把延遲拉到 400 ms 之後，
五秒仍然跑了**九個遊戲年（432 刻）**——延遲不是節流的地方。

所以早期的做法是「`Speed 3` 然後馬上 `Speed 0`」，跑幾個 frame 由事件
迴圈決定，實測一段落在 85 到 2039 次抽樣之間。段界不可控，起始的
`Fcycle`／`Scycle` 又觀察不到，只能用搜的——而搜得到是個**弱判準**，
搜尋範圍夠大時它遲早會找到某個湊得出來的起點。

正確的做法是**加觀測手段**。`tools/oracle/patches/apply.py` 給 oracle 的
原始碼加四個指令（冪等，只加觀測、不動規則）：

| 指令 | 回答什麼 |
|---|---|
| `sim Frame N` | 跑 N 個 frame（`SimFrame` ＋ `MoveObjects`），不經過事件迴圈 |
| `sim Scycle` | 五個週期性掃描的相位計數器 |
| `sim Fcycle` | 十六相位主迴圈的計數器 |
| `sim Valves` | 三個需求閥門 |
| `sim Mem <陣列> <x> <y>` | 衍生陣列的某一格（地價、汙染、犯罪、人口密度…）|

建置改在**副本**上進行（`workplace/oracle-build/`），封存的原始碼保持
乾淨——它是規則層的一手依據，不該混進我們為了觀測加的東西。

加完之後：段界精確、起點是 0／0 不必猜、分岔點是**查表**而不是搜尋，
而且分岔的原因（閥門、衍生陣列）可以直接對照。

## 二、亂數狀態就是時鐘

亂數是 24 位元的 LCG（[`02-rng.md`](02-rng.md)），而且**可逆**：
`A = 1103515245` 是奇數，模 2²⁴ 有乘法反元素，狀態能往回推。

更重要的是它的等價性：**LCG 的狀態由起點與步數唯一決定**，所以

> 「兩邊的亂數狀態相同」⟺「這一段消耗的抽樣次數一模一樣」

比對狀態就是在比對抽樣次數，而抽樣次數對得上，代表每一個「要不要抽」
的分支都走得一樣。再加上地圖零差異（每一次寫入都一樣），就是逐次元等價。

做法：

```
暫停 → 讀四次 sim Rand → 反推「開跑瞬間」的狀態 S0 → 倒出地圖
跑一段 → 暫停 → 讀四次 → 反推並倒退四步得到 S1 → 倒出地圖
Go 從 地圖 ＋ S0 出發逐 frame 推進，找 n 使得 狀態 == S1 且 12000 格全同
```

工具：`tools/oracle/tcl/frame-parity.tcl`（逐 frame）、
`tools/oracle/tcl/micro-*.tcl`（微實驗）、
`tickparity_test.go` 的 `rewindRand`／`modInverse24`。

## 三、三層對拍，由細到粗

### 3.1 微實驗：單一機制（`microzone_test.go`）

空地 ＋ 一座沒有電、沒有路的 3×3 住宅區——最小的、能走完
`doResidential → Rand(35) → evalRes → growShrink → doResOut` 的配置。

**結果：692.5 刻、1538 次抽樣、地圖零差異，逐次元完全一致。**

微實驗的價值在於把變因減到一個。地圖縮到只剩一個機制，抽樣次數就變成
一個可以直接比對的數字。

### 3.2 逐 frame 對拍：主判準（`frameparity_test.go`）

單步的 oracle 讓每一個 frame 都成為一個檢查點。資料是
`tools/oracle/tcl/frame-parity.tcl` 跑 8000 個 frame，每一步記下
`Fcycle`、`Scycle`、三個閥門與四個亂數讀數；
`tools/oracle/extract_frames.py` 把四個讀數換算成**抽樣次數**
（等價，但只要幾個位元組），存成 `testdata/frame/frames.csv`。

**結果：8000/8000 個 frame 完全一致，共 13 582 次抽樣**，
終點地圖 12 000 格零差異、資金相同。

這個判準比分段對拍強得多：分段對拍每一段都要用「200 刻收斂」重建
內部狀態，而那是虛構的——真正的閥門、成長率記憶、交通密度是從上一段
延續下來的。逐 frame 對拍從第一個 frame 一路跑到最後，中途什麼都不重設。

> 分段對拍（`segparity_test.go`、`testdata/seg/`、`tick-parity-seg.tcl`）
> 已經移除。它的起點要用搜的、段界不可控，而且判準弱——被這一節取代。

### 3.3 整段對拍：粗略護欄（`tickparity_test.go`）

四秒的長段，只看地圖差幾格。**原版改變的 108 格一格不差全部重現。**
留著當便宜的回歸護欄；嚴格的判定由 §3.2 負責。

## 四、靠這套方法抓到的錯

| 錯誤 | 症狀 | 修法 |
|---|---|---|
| 商業區成長判斷沒短路 | 塞車時多抽一次 `Rand16Signed()` | 照 C 的順序內聯 `TrfGood &&` |
| 撥款比例沒初始化成 1.0 | `roadValue` 恆為 0，資金只進不出（原版每年 −12，Go ＋9）；`RoadEffect` 也失真 | `NewWorld` 補上 `w_budget.c:82 InitFundingLevel` 的三個 1.0 |
| 投票迴圈跳過越界那一次的抽樣 | 每次評估少抽約 54 次 | 照抽不誤，比較對象取 0 |

第三項值得展開。`VoteProblems`（`s_eval.c`）的迴圈尾是

```c
x++;
if (x > PROBNUM) x = 0;     /* 不是 >= */
```

`PROBNUM` 是 10，而 `ProblemTable` 只有 `0..9`，所以 `x` 每 11 次就會走到
10、讀一次越界。**那一次的 `Rand(300)` 照樣被呼叫**，只是拿去和相鄰記憶體
比較（宣告順序是 `ProblemTable`、`ProblemTaken`、`ProblemVotes`，讀到的
多半是 `ProblemTaken[0]`，值域 `{0,1}`，幾乎永遠比不過）。

原本的 Go 寫成「索引超出範圍就跳過」——語意上看起來更安全，實際上**少抽了
一次**。每次評估最多 600 圈，等於少 54 次；亂數數列從此整條錯開。

> 教訓寫成規則：**照抄 UB 時，先分清「讀到什麼」和「有沒有讀」。**
> 讀到的值不可移植，但「有沒有消耗一次抽樣」是確定的，而且對狀態機
> 的影響遠大於那個值本身。跳過整個判斷式是把兩件事一起改掉。

## 五、怎麼定位下一個差異

1. **量速率**。長跑一段，算每刻抽幾次。原版 24.716（±0.11，
   來自 `sim Year` 只有 48 刻解析度）；Go 現在 24.820，落在區間內。
2. **拆相位**。Go 這邊可以逐 frame 記錄抽樣次數並按相位歸戶，
   看是哪個相位在耗。這座城市只有相位 2（`MapScan` 的第二段，
   三個分區中心都在裡面）與相位 9（`CityEvaluation`）在抽。
3. **對照原始碼盤點抽樣點**。`s_sim.c` 29 處、`s_zone.c` 21 處、
   `s_traf.c` 4 處、`s_eval.c` 2 處、`s_disast.c` 20 處、
   `w_sprite.c` 35 處；逐一確認在當前地圖下會不會觸發。
4. **縮到微實驗**。變因減到一個，抽樣次數就是可比對的數字。

> 反面教訓：一開始用四秒長段對拍，差異 7 格卡了很久，因為那個指標
> 同時混了「分歧點」和「分歧之後的所有下游效應」。換成短脈衝分段之後，
> 兩個真錯誤在同一輪就被定位出來。**指標的解析度決定除錯的效率。**
>
> 這條路走到底就是逐 frame：解析度到了一個 frame，「下一個差異在哪」
> 不再需要定位——它就寫在測試的輸出裡。所以上面這四個步驟現在只在
> **還沒有單步 oracle 的新題目**上才用得到；有 oracle 的話，先花半小時
> 加單步指令，比花一天用這四步定位划算。

## 六、Scycle 也要搜，不能當 0

三種分區各做一個微實驗（住宅、商業、工業），前兩個一搜相位就對上，
**工業區搜了十六個相位全部對不上**。症狀看起來像實作錯誤：

- 抽樣總數對得上（960 刻只差 33 次，而且前面幾千次完全一致）
- 地圖完全一樣（那座分區沒電沒路，從頭到尾沒長過）
- 只有 `CrimeMaxX`／`CrimeMaxY`——平手擲骰的結果——偶爾不一樣

把原版切成二十幾個檢查點逐段追，發現前十七段完全對上，第十八段斷掉；
再逐次記下抽樣的呼叫點，看到斷點落在一個 `CrimeScan` 連抽四次的 frame
中間——原版的停點是 216 次，我們的 frame 邊界從 213 直接跳到 217。

原因不在工業區，在**起始狀態少設了一個變數**：

```c
case 12: if (!(Scycle % SpdPtl[x])) PTLScan();
case 13: if (!(Scycle % SpdCri[x])) CrimeScan();
case 14: if (!(Scycle % SpdPop[x])) PopDenScan();
case 15: if (!(Scycle % SpdFir[x])) FireAnalysis();
case 11: if (!(Scycle % SpdPwr[x])) DoPowerScan();
```

最快速度下這五個分別是 `Scycle % 17／18／19／20／5`。**`Scycle` 從外面
觀察不到**（Tcl 沒有對應的存取子），所以它和相位一樣是要猜的。

Scycle 錯的話會發生的事很特別：那幾個掃描落在**不同的刻**，但它們每次
抽的次數是固定的，所以**抽樣總數還是對得上**——只有它們吃到的亂數值
不一樣。於是平手擲骰的贏家換人，而其餘一切看起來都正常，直到某個檢查點
的停點剛好落在我們某個 frame 的中間。

把 Scycle 一起搜（1024 個值 × 16 個相位，Go 跑不到一秒）之後：

| 微實驗 | 相位 | Scycle | 結果 |
|---|---|---|---|
| 住宅區 | 12 | 0 | 692.5 刻逐次元一致，地圖零差異 |
| 商業區 | 0 | 0 | 564.2 刻逐次元一致，地圖零差異 |
| 工業區 | 0 | 6 | 949.2 刻逐次元一致，地圖零差異 |

> 教訓寫成規則：**對拍前先列出「原版有、但觀察不到」的狀態，逐一決定
> 是搜還是重建。** 沒列的那一個不會報錯，它會讓對拍在一個看起來完全
> 無關的地方失敗——而那個地方（這次是犯罪掃描的平手擲骰）會把你引去
> 讀完全正確的程式碼。

### 後來 Scycle 不必再搜了

給 oracle 加上 `sim Scycle` 之後（§一），這一節的搜尋就退場了。
但**教訓不退場**：對拍前先列出「原版有、但觀察不到」的狀態，然後
**優先想辦法把它變成看得到的**——加一個唯讀存取子的成本，遠低於用
1024 個候選去搜它，也遠低於被它引去讀完全正確的程式碼。

## 六之三、需求閥門的單精度與整數除法

逐 frame 對拍上線之後，第一個分岔在**第 0 個 frame**：
`RValve` 我們算出 180，原版是 179。差 1。

而這個差 1 要跑到**第 114 個 frame** 才會變成抽樣次數的差異——那時候
某座空住宅區的 `zscore` 剛好落在成長門檻的兩側，我們多蓋了一棟房子。
在那之前，一百多個 frame 的抽樣次數完全一致。

原因在 `SetValves`（`s_sim.c:280`）兩處：

```c
float NormResPop, PjResPop, ...;
NormResPop = ResPop / 8;        /* ResPop 是 short → 整數除法！ */
```

- **`ResPop / 8` 是整數除法**，先截斷再存進 float。我們寫成
  `float64(ResPop) / 8`，多帶了小數。
- 整段是 C 的 `float`（**32 位元**），我們用 float64。幾個 double
  字面值（`.02`、`3.7`、`1.3`）還會把該次運算提升到雙精度再存回 float，
  順序也要照抄。

改成單精度 ＋ 整數除法之後，整城的粗略對拍（§3.3）直接從差 8 格
變成**差 0 格**。之前怎麼調分區規則都收不掉，因為根本不是分區的問題。

> 教訓寫成規則：**移植 C 的浮點運算時，型別就是規格。** `float` 不是
> 「浮點數」的意思，是 32 位元；`int / int` 不是除法，是截斷。
> 這兩件事都不會讓程式看起來有錯，只會讓數字差一點點——然後那一點點
> 在一百個 frame 之後變成一棟不該存在的房子。

## 六之四、對拍腳手架自己的差 4

修好閥門之後還是在第 33 個 frame 分岔，而且**閥門、地價、汙染、犯罪、
人口密度、`zscore` 全部一模一樣**（用 `sim Mem` 逐項對過）。相同的狀態
＋ 相同的亂數 = 應該有相同的結果，但沒有。

錯的是**測試的腳手架**，不是規則層：

`RecoverState` 回傳的是「**讀完那四個輸出之後**」的狀態，而原版讀完
四次 `sim Rand` 就直接跑下一個 frame——所以進入下一個 frame 的狀態
就是它。測試卻又 `advanceRand(…, 4)` 推了四步。

症狀非常隱蔽：**抽樣次數還是對得上**（偏移是常數 4，前後相減就消掉了），
只有每個 frame 實際吃到的亂數**值**整整晚四個。所以絕大多數 frame
照樣一致，直到某個分支剛好落在門檻兩側。

拿掉那四步之後：8000/8000。

> 教訓寫成規則：**對拍失敗時，先確認腳手架本身沒有引入偏移。**
> 「狀態相同、亂數相同，結果卻不同」在邏輯上不可能——出現這句話的時候，
> 「相同」的兩邊一定有一邊是自己算錯的。

## 七、診斷工具

`internal/sim/parityprobe_test.go` 有三層，資料由 `tools/oracle/` 產生後
放在 `workplace/`（不進版控），檔案不在時全部跳過：

| 測試 | 回答什麼 |
|---|---|
| `TestMicroIndSegments` | 逐檢查點追，第一個追不到的區間就是分歧點所在 |
| `TestMicroIndTrace` | 在那個區間裡逐次記下抽樣的**呼叫點**，並列出我們的 frame 邊界 |
| `TestMicroIndScycleSearch` | 把 Scycle 也納入搜尋（有 `sim Scycle` 之後只剩歷史價值）|
| `TestFrameParityTrace` | 逐 frame 對拍分岔在哪一個 frame、那個 frame 各是誰在抽樣（`SIMCITY_TRACE=1`）|

`tools/go.sh` 會把 `SIMCITY_*` 開頭的環境變數帶進容器，所以
`SIMCITY_TRACE=1` 直接寫在指令前面就行。

分岔的**原因**則靠 oracle 那邊的存取子：`sim Valves` 比閥門，
`sim Mem LandValueMem x y` 之類比衍生陣列。實際用起來是「Go 印一份、
Tcl 印一份、逐項對」——第 33 個 frame 那次就是這樣確認「兩邊完全相同」，
從而把嫌疑指回測試腳手架（§6之四）。

呼叫點的追蹤靠 `Rand.Watch`——`Rand16` 是唯一推進狀態的地方，掛一個
回呼就能逐次記下呼叫者。狀態只看得到結果，看不到來源；沒有這個鉤子
就只能猜。
