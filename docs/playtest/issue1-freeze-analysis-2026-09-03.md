# issue #1 第三項「畫面變雪花亂碼卡死，音樂持續」— 程式流程分析

回報內容（2026-09-02，issue #1）：「蓋了一段時間後，整個畫面會變成雪花亂碼卡死，
但音樂持續。」六分鐘的壓力測試沒有重現（`WORKLOG.md` 2026-09-03 那一節），
所以這一輪改成逐條走程式流程，把「能造成這個症狀的機制」一個一個排除。

## 結論

1. **音效播放器沒有被關掉，也沒有被留住參考。** `internal/ui/sound.go` 每次發聲
   都 `NewPlayerFromBytes` 再 `Play()`，然後把 `*Player` 丟掉。Ebiten 的
   `audio.Context` 只在 `playingPlayers` 裡持有 `playerImpl`（`audio.go:265`），
   不持有 `*Player` 本身，而 `NewPlayer` 對 `*Player` 註冊了
   `runtime.AddCleanup(p, (*playerImpl).finalize, …)`（`audio.go:347`）。
   兩個後果：播放器數量在遊玩期間**沒有上界**，而且 GC 可以在聲音還在播的時候
   把它收掉。驗證方法：Inspection（讀 Ebiten v2.9.10 的原始碼）。
2. **上一輪的壓力測試是 `-mute` 跑的**，所以它的負面結果**不涵蓋音效那條路**——
   而工具音正是「蓋城市」會一直觸發的東西。驗證方法：Inspection
   （`tools/stress_ui_inner.sh` 第 9 行）。
3. **模擬層沒有沒有上界的迴圈。** 全檔掃 `internal/sim` 的條件式迴圈只有六處，
   逐一看過都有上界：`power.go` 的電力掃描由 `maxPower` 夾住、
   `eval.go:143` 由 `z < 100 && count < 600` 夾住、`terrain.go` 的兩處由
   `InBounds` 夾住、`rand.go:88` 的拒絕取樣要 `n ≥ 65536` 才會空轉，
   而全部呼叫端傳的都是常數或世界尺寸。驗證方法：Inspection。
4. **專案自己沒有第二條 goroutine**（除了這一輪之後才加的卡死偵測器），
   所以「另一條執行緒把地圖改壞」這一類的資料競爭在程式碼層面不成立。
   驗證方法：Inspection（全樹 `grep "go func"`）。
5. **音效事件佇列有上限 16**（`internal/sim/sound.go`），精靈用完會從串列摘掉
   （`sprite.go:117 destroySprite`），介面影像都有快取不逐格配置。
   這三條常見的洩漏路徑都已經堵住。驗證方法：Inspection。
6. **每個畫格最多跑三次模擬**（`simFramesPerTick`），單次成本由 120×100 的地圖
   夾住，不隨遊玩時間成長。所以「愈玩愈慢直到停住」不是模擬層造成的。
   驗證方法：Inspection。

症狀的三個部分要分開看：**音樂持續**代表行程還活著；**畫面不動**代表主迴圈沒有
再送出畫格；**雪花**代表視窗顯示的是未定義內容——那是「停止呈現」的結果，
不是「畫錯東西」的結果。程式碼裡找得到的、能讓主迴圈停止呈現的機制，
目前只剩資源耗盡一類，而唯一還沒有上界的資源就是第 1 點。

## 建議

1. 把音效播放器改成留參考、播完關掉、同時活著的數量設上限。**已改**
   （`internal/ui/sound.go`：`live []livePlayer`、`reap()`、`maxLivePlayers = 16`）。
2. 壓力測試不要再靜音跑。容器沒有音效裝置，用 ALSA 的 null PCM 頂上即可
   （`-audio-probe` 在該設定下回 0）。**已改**（`tools/stress_ui_inner.sh`）。
3. 壓力測試要換縮小倍率。`buildZoom` 對 960 張圖塊逐像素做 GPU 讀回
   （`internal/ui/tileset.go` 的 `shrink` 用 `src.At`），是呈現層最重的一段，
   固定倍率跑一整輪等於沒測到它。**已改**（同上）。
4. 顏色數的門檻改成「第一次量到的值的兩倍」。原本寫死 64，而實測基準是 700 上下，
   等於每一列都被標成異常——一個永遠亮著的警報等於沒有警報。**已改**（同上）。
5. 下一次真的卡住時以 `chengshi-freeze-*.log` 的 goroutine 堆疊為準
   （`-watchdog`，預設 10 秒）。**在這份報告的所有推論之上，那份現場才是證據。**

## 假設

- 回報者跑的是 Linux 上的發行包或 AppImage，用真的顯示卡驅動。**未經確認**——
  已在 issue 回問環境，還沒有回覆。
- 「雪花亂碼」指的是整個視窗變成隨機像素，不是地圖畫成錯誤的圖塊。
  兩者的成因完全不同：前者是停止呈現，後者是圖塊查表出錯。
  `TileImage` 對超出範圍的編號回第 0 張而不是越界讀（`tileset.go:290`），
  所以後者在程式碼層面已經被擋掉。
- 「音樂持續」指的是背景音樂（玩家自備的檔案）沒有斷。

## 方法

1. 全樹列出 `internal/sim`、`internal/ui`、`internal/game` 的條件式迴圈，逐一判上界。
2. 全樹找 `go func`，判有沒有跨執行緒共享狀態。
3. 全樹找 `ebiten.NewImage`／`NewImageFromImage`，判有沒有逐格配置。
4. 追每一條會在遊玩期間成長的資料結構：音效佇列、精靈串列、播放器、影像快取。
5. 讀 Ebiten v2.9.10 的 `audio` 套件，確認播放器的生命週期由誰持有。

`MINUTES=5 tools/stress_ui.sh`，這一輪**開音效**（ALSA null PCM）並加入

| 指標 | 結果 |
|---|---|
| 顏色數 | 684–704，基準 695，沒有暴增 |

| CPU 秒 | 持續前進，沒有停住 |
| 卡死報告 | 沒有產生 |

驗證方法：Test。**這是負面結果**：症狀沒有重現，所以它既不能證實也不能否證

不會凍、畫面正常**。

## 有效性威脅

- **內部效度**：這一輪修掉的東西是「讀程式碼找到的缺陷」，不是「重現後定位到的成因」。
  修好之後症狀沒有再出現，也不能反推它就是成因——因為症狀本來就沒有在這裡重現過。
  緩解：把判準交給卡死偵測器的現場，不靠這份分析下定論。
- **外部效度**：所有驗證都在 docker ＋ Xvfb ＋ llvmpipe 軟體 GL 上做。
  真實顯示卡驅動的失效模式（材質配置失敗、context lost）在軟體 GL 上不會出現，
  而症狀描述最像的就是那一類。緩解：無——這是這台機器的硬限制，
  要靠回報者的環境資訊或在有顯示卡的機器上重跑。
- **建構效度**：壓力測試量的三個數字（顏色數、RSS、CPU 秒）能分辨
  「無窮迴圈 vs 死鎖 vs 洩漏」，但**量不到 GPU 端的資源**。
  螢幕變雪花時顏色數會暴增，這一項成立；驅動先崩潰導致行程被殺則量不到。
  緩解：加上「行程還在不在」的檢查（已有）。
- **結論效度**：第 3、4、5、6 點是靜態掃描的結果，強度取決於掃描有沒有漏。
  條件式迴圈用的是 `^\s*for [^;{]*{\s*$` 這個樣式，**掃不到寫成一行的迴圈與
  遞迴**。緩解：遞迴另外查過（規則層沒有遞迴函式），一行式迴圈在本專案的
  程式風格裡不存在，但後者沒有機械化的保證。
  遞迴是用「函式本體出現自己的名字」掃的，`internal/sim`／`ui`／`game`
  三層命中兩筆，逐一看過都是誤判（一筆命中的是註解裡的 `Rand(`，
  另一筆是 `Frame()` 呼叫 `SimFrame()`，不是 `SimFrame` 呼叫自己）——
  **沒有自我遞迴的函式**。
